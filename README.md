# Itemator

**One click for what was asked. A name for anything more.**

When an AI agent or a new teammate opens a merge request, someone approves it, often with one click. Anthropic reports that Claude Code users approve 93% <!-- from: results/external_figures.json:approval_rate_claude_code_permission_prompts.value --> of permission prompts, and calls the result approval fatigue ([source](https://www.anthropic.com/engineering/claude-code-auto-mode)). A merge request has the same problem: the change that was asked for is easy to check, and the extras that came with it are not.

Itemator lists what a merge request changed beyond its linked issue, and asks a person to name each extra before it merges. Changes that stay inside the issue keep the normal one-click approval. Other tools already flag out-of-scope changes (see Related tools); here each extra gets its own thread, a typed answer, and a record of who decided.

**On a real agent.** We gave GitLab's own Developer Flow the issue "make the itemator job faster". It changed only `.gitlab-ci.yml`, a file the issue never mentions. Itemator opened a thread on that file, the approver typed its name, and the flow recorded who kept it.

**With auto-merge armed.** The organisers' reference app lifts Draft and arms auto-merge from a CI job, inside the pipeline, before any card exists. With the project's optional hold on, we armed auto-merge while the first pipeline was still running: the `itemator` job failed on purpose (it says an extra is not named yet), GitLab kept the merge blocked, the card posted its thread, the approver typed the name, and after one retry of the `itemator` job GitLab merged the merge request by itself. Without the hold, a thread that is already open also holds the merge (`discussions_not_resolved`), but a merge armed before the card exists can go through first. The retry is a manual click, and it needs "Pipelines must succeed" on in the project (one run, one project).

**Status:** built for GitLab's *Life After Code* hackathon (Path A, Supervised). Every figure written in digits that comes from our own runs sits next to a pointer to the results file that produced it, and a CI check (`tools/hardcode_audit.py`) enforces that.

## How it works
1. **A CI job lists the extras.** The `itemator` job reads the merge request's diff and its linked issue and applies fixed rules (`itemator/extras.py`): a new dependency, a CI or config change, removed tests, a removed public function, deleted generated code, a committed binary, large file or build output, a version bump, a stray file. No model decides whether an extra exists. It writes `itemator.json`.
2. **A GitLab Duo flow posts the card.** `flows/itemator_card.yml` starts by itself when the pipeline of a merge request a person opened finishes. In our runs GitLab did not start the flow from the pipeline of a merge request an agent opened, and its [trigger documentation](https://docs.gitlab.com/user/duo_agent_platform/triggers/) says why: every trigger needs a human to perform the action, and a bot or service account cannot start one. So for such a merge request, a person assigns the card account as reviewer, which is a normal reviewer step. The card is two lines: what is beyond the issue, and what the approver does next. Each extra gets its own resolvable thread on the line it changed, and the merge request is set to Draft.
3. **The approver answers in the thread** with one word each: the extra's exact name keeps it, `not an extra` dismisses it, `split` moves a CI or config file or a package manifest into its own merge request, `remove` takes it back out of this one (like `split`, only for whole CI or config files, or a manifest whose only change is the named package; `remove` also takes back a file the merge request adds). The thread offers only the answers the flow accepts for that extra. `flows/itemator_react.yml` reads the answers when someone mentions its account or marks the merge request ready. It records who typed what, reopens a thread that was resolved without a name, and takes Draft off when every extra is settled. Its summary lists each extra with who decided, and says so when the author typed every answer.
4. **For a new dependency the thread also carries facts from PyPI, npm or crates.io, and OSV**: whether the package exists, when it was first released, how many releases it has, its licence as the publisher declares it, and the number of known advisories. Only facts; no score. The lookup validates every name, reaches four hosts, and never fails the job.
5. **A team can set its own rules in `.itemator.toml`**, read from the branch the merge request targets, so the merge request cannot change the rules it is judged by. The file can require that someone other than the author names each extra, or quiet whole kinds of extras and paths; it can never quiet a binary file, a change to the policy itself, or a dependency the registry did not find. The `itemator` job also runs the checker exported from the target branch, and ignores git attributes in the checkout, so a merge request cannot hide its diff.

6. **Each thread says whether the author's own description mentions the extra**, in one of three fixed sentences: it lists the extra under a `Beyond the issue` heading, it names it, or it does not mention it. None of the author's words is ever copied into the thread, and the extras the description does not mention come first. It is a fact, not an approval: an author who names every extra still gets every thread. Across the 75 <!-- from: results/silent_extras.json:summary.per_sample.total.extras --> extras the rules found in our five samples, the pull request's own text named 12 <!-- from: results/silent_extras.json:summary.per_sample.total.named --> (a plain word match; a paraphrase does not count).
7. **An answer can become a team rule, through review.** For an extra that is a single CI or config file or a stray file, the thread also offers `always`. The flow keeps the extra and opens a merge request into the target branch whose whole change is one line of `.itemator.toml` (the file is added to `ignore.paths`); merging it stops the questions about that file on later merge requests. Binaries, agent instruction files, package manifests and changes to the policy are never offered. We ran this end to end on a throwaway branch, and again after the reaction flow's prompt was tightened (the one-line check now reads the diff GitLab reports): the answer opened the one-line merge request, and after it was merged the same edit in a new merge request was listed as quieted by the team policy. It is a choice for a team to make, and it trades fewer questions for more silence. A policy merge request that no issue describes also gets a thread, for the policy file itself, and stays in Draft until a person links the issue it answers (we checked this on a throwaway branch).
8. **An optional hold** (`names.hold_until_named = true` in the policy). The `itemator` job then fails while a kept extra has no name, and passes again when the reaction account's summary for the current head commit exists (retry the job after the last name). It is meant for loops that arm auto-merge inside the pipeline, where GitLab could otherwise merge before the card exists; it needs "Pipelines must succeed" in the project. Run live once in the reference app's order (see the top of this page); it needs one manual retry of the job after the last name, and it showed that the card flow had to read a job that failed on purpose. What defeats it: the job is defined in the merge request's own CI file, so a merge request that edits `.gitlab-ci.yml` (the kind of extra the hold is for) can drop the job or let it fail; and for an agent's merge request no card appears until a person assigns the card account as reviewer, so the job stays held with no thread to answer. We tried eight ways to merge past it on a throwaway branch ([results/bypass_matrix.json](results/bypass_matrix.json)): 2 <!-- from: results/bypass_matrix.json:merged --> of the 8 <!-- from: results/bypass_matrix.json:attempts --> merged (a merge request that marks the job allowed to fail, or that stops it from running), and 6 <!-- from: results/bypass_matrix.json:blocked --> were blocked, two of them (deleting the job, emptying its script) only because our own unit tests read the CI file and failed.
9. **The person who wrote the issue decides** (`names.asker_required` in the policy; six pre-registered replies ran twice live, on two versions of the flow, and 12 <!-- from: results/asker_study.json:as_expected --> of 12 <!-- from: results/asker_study.json:cases --> ended as expected; the record on the issue has not run live yet). When it is on, each thread says `Only the person who wrote the linked issue (@alice) can keep this.`, the reaction flow counts a name, `not an extra` or `always` only from that person, and when every extra has an answer it posts a record on the issue listing what went beyond it and who decided each. A GitLab Insights chart (`.gitlab/insights.yml`, Ultimate) counts merge requests per week by the label the flows left on them.
10. **The merge box can say no** (not yet run live). If the project has an approval rule that lists the reaction account, the reaction flow posts `/approve` only after every extra has an answer for the current commit, and only if the card for that commit exists. GitLab's own settings do the rest: its approval settings already stop the author approving and remove approvals when commits are added. We have not yet shown that a `/approve` note from a service account counts as an approval.
11. **A decision log after the merge** (`itemator/decisions.py`, CI job `decision-log`). The reaction flow ends each merge request with one summary note that lists every extra and who named it. The job reads those notes for the merge requests merged since the previous tag (only notes written by the reaction account are believed, and titles and names are stripped of links and mentions before they reach a release), and on a tag it puts the result in the release description; run by hand on the default branch it gives the same report for the last thirty days. It reads merge requests and notes with the job token and writes nothing but the release description. Its first real run was on the merge request that applied the second audit's fixes, which Itemator judged itself: it listed 1 <!-- from: results/decision_log_run.json:stats.merge_requests --> merge request with 2 <!-- from: results/decision_log_run.json:stats.extras --> extras, both kept by their author ([results/decision_log_run.json](results/decision_log_run.json)). The release path also ran once on a throwaway tag, which wrote the same section into a new release and was deleted afterwards; the first real release will be the submission tag.
12. **Two Agent Skills** (`skills/`) sit in `skills/`; GitLab's Developer Flow read the first one with no setup (one run, below). `stay-inside-the-issue` is for an agent that opens a merge request: keep to the issue, and list anything that needs a person's decision under a `Beyond the issue` heading in the description. `answer-an-itemator-card` helps whoever reads the card: what the lines and the four answers mean. It explains and never answers for the approver.

To install it in your own project, see [docs/setup.md](docs/setup.md).

**Real agent runs.** We assigned two small issues to GitLab's own Developer Flow. For the first (look up registry facts in parallel) the agent changed only the code and its tests, and the card said so. For the second ("make the itemator job faster") it changed only `.gitlab-ci.yml`, a file the issue never mentions: Itemator flagged it, the approver typed the name, and the flow settled it. An agent that changes how a job runs is doing what it was asked, and a person still decides to keep it. We then added the first skill and gave the Developer Flow the same issue again: this time its description ended with a `Beyond the issue` section naming `.gitlab-ci.yml` and why. That is one run on one issue, so it shows that the skill is read, not how often it helps. The rules still flag the file either way; the skill only makes the agent say it.

**Eight runs written down first.** Later we wrote eight issues before running any of them ([eval/field_study_issues.json](eval/field_study_issues.json): four plain, two that tempt an agent to add a package, two that name a CI change) and gave each to the Developer Flow, one at a time, with `AGENTS.md` and the skill in place. It opened a merge request every time, with a median of 17.5 <!-- from: results/field_study.json:tool_calls_median --> tool calls. The `itemator` job found no extra in any of the eight (in two it could not place one file, which the card does not show when the issue's author opened the run), and every description had a `Beyond the issue` section: five said "Nothing", three listed edits the agent made. So with those two files in the repository the rules found nothing beyond the issue, and the card asked no question. The section test was made stricter after the first two runs and applied again to their saved descriptions, and the tool-call counts were read again after every session had ended. That does not show the problem is rare: it is eight runs of one agent on issues we wrote, all started by the person who wrote them, and we ran no control without `AGENTS.md`. The counts are in [results/field_study.json](results/field_study.json); nothing was merged.

Every step ran live on GitLab.com in this project, on throwaway merge requests and issues in this project, closed afterwards. The merge requests that tested naming, `split` and `remove` were prepared by us with planted extras (a made-up package name, a comment line in the CI file, a backup file). The Developer Flow runs above were not prepared: the agent's own work on issues we wrote.

## How often agent pull requests get a second look
Itemator exists because a merge request that changes more than its issue asked for depends on someone noticing. The same AIDev data shows how often a human comments on these pull requests. Of the 1610 <!-- from: results/review_stats.json:overall.merged --> merged agent pull requests that link an issue (in public repositories with a permissive licence):

- 59% <!-- from: results/review_stats.json:overall.shares.merged_no_human_inline_comment --> had no comment by a human on any line of the diff.
- 18% <!-- from: results/review_stats.json:overall.shares.merged_no_human_review --> had no review by a human at all.
- Of those that did have a human review, 32% <!-- from: results/review_stats.json:overall.shares.merged_human_reviewed_only_empty_approvals --> held only approvals with no text.
- The median time from opening to merging was 1118.9 <!-- from: results/review_stats.json:overall.time.median_minutes --> minutes, so these are not instant merges.

This does not say anyone was careless. Reviews and talk outside GitHub are invisible here, an empty approval may follow a careful read, and the pool is mostly one agent (Copilot). It sizes how often a human leaves a written trace on a line, which is what an extra needs to be caught. Of the 8 <!-- from: results/review_stats.json:flagged.merged --> merged pull requests that rules v4 flagged in our samples, 0 <!-- from: results/review_stats.json:flagged.merged_with_human_inline_comment --> had a human comment on any line. The definitions and the per-agent split are in [results/review_stats.json](results/review_stats.json).

## How the rules are tested
The rules and the CI job are unit-tested, and also mutation-tested: a script breaks one line at a time and a test has to fail. The manual `mutation-suite` job in this project's pipeline ran 695 <!-- from: results/mutation.json:total_mutants --> mutants (182 <!-- from: results/mutation.json:rules.mutants --> on the rules, 513 <!-- from: results/mutation.json:job_and_flows.mutants --> on the CI job, the policy file and the reaction flow's prompt text) and every one was caught ([results/mutation.json](results/mutation.json), with both logs). Several mutants survived at first and each one showed a missing test, which we added; a first run counted one mutant that did not compile as caught, the second audit found it, and the runners now report such a mutant as invalid. A caught mutant shows that a test notices the change, not that the rule is right: that is what the labelled samples below are for.

## Related tools
Other tools already flag changes beyond the ask. As their own pages describe them on 2026-10-11, none asks the approver to name each extra inside GitLab:
- CodeRabbit checks a pull request against its linked issue and can block ([pre-merge checks](https://docs.coderabbit.ai/pr-reviews/pre-merge-checks)).
- unasked compares a change with the agent's prompt ([PyPI](https://pypi.org/project/unasked/)); MergeWarden compares it with declared paths ([Product Hunt](https://www.producthunt.com/products/mergewarden)).
- GitLab's own Code Review Flow reviews a merge request from its title, description and diff ([docs](https://docs.gitlab.com/user/duo_agent_platform/flows/foundational_flows/code_review/)).

Itemator's claim is narrower than detection: one thread per extra, a typed name, in GitLab, against the linked issue.

## Which lifecycle stages it touches
We count a stage only where Itemator reads or writes something in it:

| Stage | What Itemator does there |
|---|---|
| Plan | Reads the linked issue and checks the change against what it says |
| Create | Reviews the merge request, opens one thread per extra, moves or removes an extra |
| Verify | Runs as a CI job on every merge request pipeline; starts a Duo flow when it finishes |
| Package | Looks up new dependencies on their public registries |
| Secure | Shows advisories and licences for new dependencies; flags committed binaries and build output |
| Configure | Reads a team policy from the target branch; the flows and skills are set up per project |
| Govern | Records who decided each extra; the policy can require a second person |
| Release | On a tag, the `decision-log` job writes into that release's description which extras shipped since the previous tag and who decided each |
| Monitor | The same job, run by hand for any window, reports how extras were decided (kept, dismissed, moved, removed) and how many names the merge request's own author typed alone. It watches the review process, not a running service |

That is all nine stages the organisers list. Release and Monitor are the thinnest of them: one read-only job each, written on 2026-10-13.

## Known limits
- **The lock is a project setting.** Each extra is a resolvable thread, and the merge button stays blocked while a thread is open only if the project turns on "All threads must be resolved". In this project it is on (an organiser updated our role and we turned it on): we checked that a merge with an open thread is refused ("discussions not resolved") and goes through once the threads are answered. Our role cannot change that setting through the API, so another team has to tick it itself; without it an unnamed extra only puts the merge request in Draft. A person's own comment that mentions the reaction flow also becomes a thread, so the flow resolves it at the end of its run. We tested auto-merge on a throwaway branch with a thread already open: GitLab kept the merge at `discussions_not_resolved`, and after the name was typed it merged by itself within two seconds, with no other click. The reference app arms the merge inside the pipeline, before any thread exists: only the optional hold, described under How it works, covers that order, and it was run live once. A `split` or `remove` adds a commit to the branch, which GitLab's documentation says cancels an armed auto-merge until it is armed again.
- **The job is defined in the merge request's own CI file.** A merge request that rewrites the `itemator` job can hide its extras. Real use needs the job pulled in from a protected include or a pipeline execution policy that the merge request cannot edit; the role we hold here cannot set that up.
- **Author-typed names.** A solo author can type every name. The summary says when that happened, instead of hiding it. With `other_person_required` in the team policy, the author's own replies do not count; we tested that a second account's replies do.
- **Rules miss things.** For example, a one-line edit of a dependency list in `pyproject.toml` was missed until a live test found it (fixed in rules v4). The audits list more.
- **The approved event is untested.** The flow can react when a merge request is approved, but a second approver is needed to test it, and we have not.
- **No hook on merge.** GitLab's merge trigger is off by default, so no record is written at the moment of merging; the summary note lists who named what once the last extra is settled.
- **Split and remove are narrow.** Both take whole CI or config files, or a manifest whose only change is the named package; remove also takes back a file the merge request adds. Anything else is refused with a reason.
- **Anyone who can comment can answer.** On a public project any GitLab user can type a name or `not an extra`; only `split` and `remove` are limited to the author, assignees and reviewers.
- **A model follows the reaction steps.** Code decides which extras exist; the Duo model checks replies with the fixed string tests in `flows/itemator_react.yml`. It passed our live tests. We also wrote eight replies down first ([eval/react_study_cases.json](eval/react_study_cases.json): an exact name, a name in backticks with a full stop after a wrong reply, a dismissal, `remove`, a name in upper case, another thread's name, an instruction aimed at the flow, a name typed with the mention) and ran them once on a throwaway merge request: the flow ended as expected on 8 <!-- from: results/react_study.json:as_expected --> of 8 <!-- from: results/react_study.json:cases -->, including the three that had to stay open. A first list of thirteen, which also held a question and "keep it", was replaced before any run because the rules put stray files in one thread; those two cases are not in the list that ran. That is one run of one model on cases we wrote, so it is not a misread rate ([results/react_study.json](results/react_study.json)).
- **Typing is not reading.** We have not measured whether typing a name changes what approvers do. What it changes for certain is the record: each extra says who kept it. Recall is not measured either, only precision.

## Why Python
