# Known limits, the rest

The README lists six; these are the others.

- **Tested on public projects only.** The `itemator` job and `scan-history` read the merge request and its issues through GitLab's API, first without a token and then with the job token. GitLab's job token can read merge requests and their notes but not issues ([job token docs](https://docs.gitlab.com/ci/jobs/ci_job_token/)), so in a private project the issue reads would fail; we have not run it there.
- **The lock is a project setting.** Each extra is a resolvable thread, and the merge button stays blocked while a thread is open only if the project turns on "All threads must be resolved". In this project it is on (an organiser updated our role and we turned it on; said in the hackathon's Discord channel, which is not public): we checked that a merge with an open thread is refused ("discussions not resolved") and goes through once the threads are answered. Our role cannot change that setting through the API, so another team has to tick it itself; without it an unnamed extra only puts the merge request in Draft. A person's own comment that mentions the reaction flow also becomes a thread, so the flow resolves it at the end of its run. We tested auto-merge on a throwaway branch with a thread already open: GitLab kept the merge at `discussions_not_resolved`, and after the name was typed it merged by itself within two seconds, with no other click. The reference app arms the merge inside the pipeline, before any thread exists: only the optional hold, described in [docs/how-it-works.md](how-it-works.md), covers that order, and it was run live twice, the second time with the job injected by the policy. A `split` or `remove` adds a commit to the branch, which GitLab's documentation says cancels an armed auto-merge until it is armed again.
- **A stopgap is found by its lines.** The `until #N` check compares the lines its merge request added with the file at the head. A stopgap moved to another file, or rewritten so that none of its longer lines stays the same, counts as taken out. One that lives in several files is named by the one file its thread was on. Stopgaps kept in another project's issue are not read.
- **Some reads need a public project.** On gitlab.com the CI job's token cannot read a merge request's threads, an issue's comments or the member list (we probed it from a CI job on 2026-10-24), so the job reads them through GraphQL without a token, which works only on a public project. On a private project the hold's re-check of the answers falls back to the reaction account's summary and the job says so, and a stopgap kept `until #N` is not asked about again.
- **Malware is named only once someone has reported it.** The thread names a package OSV has a malware report for; a package nobody has reported yet looks like any other new dependency, with its registry facts. When OSV cannot be read, the thread says no more than before.
- **A pin in a file is not what runs.** The left-behind check reads files. A build argument, a compose `build.args` value or a CI variable can override a version at build time; an image can be rebuilt under the same tag; a running container keeps its old image until it is redeployed (`php -v` inside it is the real check); a Helm chart that splits `repository:` and `tag:` and a copy bundled inside another image are not read. It reads YAML by indentation and key, so an `image:` line inside a script block can be read as a pin.
- **The CI-lint guard is a table typed by hand.** The job skips GitLab's CI lint on the versions GitLab's October 2026 patch notes list for its regular-expression flaws. A later flaw is not covered until someone adds its ranges to `pipeline.UNSAFE_LINT`, and a self-managed GitLab that hides or rewrites its version string is read as one the job cannot tell, so the pipeline line is left out there.
- **The check lives in a policy.** A merge request that rewrites the `itemator` job can hide its extras. The job is injected by a pipeline execution policy that the merge request cannot edit (the organisers added the policy-link ability to our role on 2026-10-14; said in the hackathon's Discord channel, which is not public). We ran GitLab's Developer Flow once on an issue we wrote first: the merge request it opened got the injected job, and the job passed (policy_job_in_agent_pipeline in [results/policy_run.json](../results/policy_run.json)). Anyone who can push to the default branch can still change the checker (`itemator/` here, which the job runs from the target branch), and so can a flow account that holds `create_commit`; the job file itself is kept in the policy project, which the flow accounts cannot push to, and the job `policy-job-in-sync` fails when the copy here differs from it. Protecting the branch needs a role we do not have. Another project needs that ability or an Owner, and GitLab's copy of a policy lags a few minutes behind its policy project.
- **Author-typed names.** A solo author can type every name. The summary says when that happened, instead of hiding it. With `other_person_required` in the team policy, the author's own replies do not count; we tested that a second account's replies do.
- **It does not catch what GitLab's reviewers catch.** On GitLab Duo's own merge requests in gitlab-org/gitlab, the parts people objected to were almost all source code, tests and docs, which the rules have no kind for; the rules listed none of them ([results/gitlab_scope_v6.json](../results/gitlab_scope_v6.json)). Itemator names the kinds of change a one-click approval skips (dependencies, CI and config, binaries, generated files, agent instructions); reading the code is still the reviewer's job.
- **A word in the issue can hide a dependency.** The rule treats a package as asked for when the issue contains its name, so an issue that says "handle more requests" would hide a new `requests`. An outside reviewer showed this on a test repository. On the 300 <!-- from: results/name_match_v1.json:pull_requests --> held-out agent pull requests it happened 4 <!-- from: results/name_match_v1.json:silenced --> times, and each time the issue did mean the package (for example "Uses azure-appconfiguration-provider"); none was a word used in another sense, so a stricter match would have turned all four into false alarms ([results/name_match_v1.json](../results/name_match_v1.json), read by our coding agent, one reader). An issue that must be exact can declare its scope instead (an `itemator-scope` block listing paths and dependencies, [setup](setup.md#an-issue-can-declare-its-own-scope-optional)); the check then uses the list and not the words. MergeWarden compares a change with a declared scope too.
- **The approved event is untested.** The flow can react when a merge request is approved, but a second approver is needed to test it, and we have not.
- **No hook on merge.** GitLab's merge trigger is off by default, so no record is written at the moment of merging; the summary note lists who named what once the last extra is settled.
- **Split and remove are narrow.** Both take whole CI or config files, or a manifest whose only change is the named package; remove also takes back a file the merge request adds. Anything else is refused with a reason.
- **The diff sentence is a model's reading.** The card's one sentence on what an extra's file does is written by the flow's model from the diff, not by the rules. It is told to describe and never judge, and to flag text addressed to automated reviewers without repeating it; results/read_live.json records the one live check of that.
- **Patch-day mode reads versions loosely.** Any dotted number in a CVE issue counts as a listed version, including a CVSS score. A fix that needs code changes as well as the bump asks once about each code file; answer it with its name, or put an `itemator-scope` block in the issue.
- **The GitHub copy lags and is squashed.** The owner copies GitLab main to [GitHub](https://github.com/Anbu-00001/Itemator) by hand, one commit per copy, so GitHub can be behind and its history is not commit for commit. `python3 tools/check_mirror.py` says which GitLab commit it matches and how many newer commits GitLab has. Two matching copies show only that neither host changed the files since the copy; they say nothing about whether the code itself is safe.
