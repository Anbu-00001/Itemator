# How Itemator works, in full

The front page ([README](../README.md)) has the pitch, the diagram and the first three steps. This page has the rest of the steps and the live runs behind them.

## What each flow can write
The tool lists are in the flow files (`toolset:`). A tool a flow does not hold, it cannot call; what a held tool is told to do is in the flow's prompt, which our tests read (and which a hostile text could in principle argue with: see the injection study in [docs/measurements.md](measurements.md)).

| Flow | Tools that change something | What we use them for | Tools it does not hold |
|---|---|---|---|
| Card (`flows/itemator_card.yml`) | `create_merge_request_note`, `create_merge_request_diff_note`, `update_merge_request` | the card, one thread per extra on the changed line, Draft and labels | any commit or branch tool, any approval, any merge |
| Reaction (`flows/itemator_react.yml`) | `reply_to_discussion`, `set_discussion_resolved`, `create_merge_request_note`, `update_merge_request`, `create_issue_note`, `create_commit`, `create_merge_request` | answers in threads, the summary, labels and Draft, the record on the issue; `create_commit` and `create_merge_request` only for `split`, `remove` and `always`, each asked for by a typed answer | any approval, any merge |

The commit and merge-request tools are the widest ones. The reaction flow's prompt limits them to the merge request's own branch (`split`, `remove`) and to one new branch for the one-line policy change (`always`); a prompt is not a permission, and a stricter setup would split the reaction flow in two so the commit tools sit in a flow that only a `split`, `remove` or `always` reply can start. We have not built that split.

## The other steps

4. **For a new dependency the thread also carries facts from PyPI, npm, crates.io or the Go module proxy, and OSV**: whether the package exists, when it was first released, how many releases it has, how many days before the check the pinned version came out (said only when that is within a month), its licence as the publisher declares it, and the number of known advisories. Only facts; no score. The lookup validates every name, reaches seven hosts (pypi.org, registry.npmjs.org, crates.io, api.nuget.org, proxy.golang.org, api.osv.dev and api.deps.dev), and never fails the job. For a Go module the proxy gives the tagged versions and two dates (the lowest-numbered version, taken as the first release, and the pinned one) but no licence, and the card says so instead of "no licence stated". Three more facts are said only when true: that installing the version runs code of its own (npm: an install script, from the registry's own `hasInstallScript` flag or a `preinstall`, `install` or `postinstall` script; PyPI: no wheel, so pip builds it from source and runs its build code), that its npm publisher marked it deprecated, or that the PyPI version is yanked. A dry run on the registries read esbuild 0.24.0 as running an install script, request 2.88.2 and left-pad 1.3.0 as deprecated, and pycrypto 2.6.1 as having no wheel.
   For a PyPI or npm package the card also says what keeping it costs every fresh install: deps.dev's resolved dependency graph for the version used, the number of packages in it, and the sum of their download sizes from each registry (the wheel pip would most likely take on a Linux runner, or the npm tarball). It then multiplies that by the pipelines the project ran in the last month, read from the GitLab API, and says "if each one installs it without a cache", because a pipeline with a cache does not. A size a registry does not give is counted as unknown and the total becomes "at least". Go, NuGet and Cargo are not weighed: deps.dev gives no graph for the first two, and its Cargo graph includes dev-only dependencies. When a person replies `remove`, the decision log adds up the weight the job measured (read from its own report, never from comment text) for removed and for kept dependencies, so a release says how much was kept out of every fresh install, as an upper bound: some of those packages may already be installed for another reason. The wheel is our reading of pip's choice (the most specific tag first), not pip itself.
   NuGet packages added in `.csproj`, `.fsproj`, `.vbproj`, `Directory.Packages.props`, `Directory.Build.props` or `packages.config` get the same facts in the card's "Also checked" sentence, not in a thread: the extras rules do not read .NET build files, so these packages are not extras and never hold a merge. A package an older line of the same file already listed is a version change and is skipped; a version range or property is not looked up as a pin.
5. **A team can set its own rules in `.itemator.toml`**, read from the branch the merge request targets, so the merge request cannot change the rules it is judged by. The file can require that someone other than the author names each extra, or quiet whole kinds of extras and paths; it can never quiet a binary file, a change to the policy itself, or a dependency the registry did not find. The `itemator` job also runs the checker exported from the target branch, and ignores git attributes in the checkout, so a merge request cannot hide its diff.

6. **Each thread says whether the author's own description mentions the extra**, in one of three fixed sentences: it lists the extra under a `Beyond the issue` heading, it names it, or it does not mention it. None of the author's words is ever copied into the thread, and the extras the description does not mention come first. It is a fact, not an approval: an author who names every extra still gets every thread. Across the 75 <!-- from: results/silent_extras.json:summary.per_sample.total.extras --> extras the rules found in our five samples, the pull request's own text named 12 <!-- from: results/silent_extras.json:summary.per_sample.total.named --> (a plain word match; a paraphrase does not count).
7. **An answer can become a team rule, through review.** For an extra that is a single CI or config file or a stray file, the thread also offers `always`. The flow keeps the extra and opens a merge request into the target branch whose whole change is one line of `.itemator.toml` (the file is added to `ignore.paths`); merging it stops the questions about that file on later merge requests. Binaries, agent instruction files, package manifests and changes to the policy are never offered. We ran this end to end on a throwaway branch, and again after the reaction flow's prompt was tightened (the one-line check now reads the diff GitLab reports): the answer opened the one-line merge request, and after it was merged the same edit in a new merge request was listed as quieted by the team policy. It is a choice for a team to make, and it trades fewer questions for more silence. A policy merge request that no issue describes also gets a thread, for the policy file itself, and stays in Draft until a person links the issue it answers (we checked this on a throwaway branch).
8. **An optional hold** (`names.hold_until_named = true` in the policy). The `itemator` job then fails while a kept extra has no name, and passes again when the reaction account's summary for the current head commit exists (retry the job after the last name). It is meant for loops that arm auto-merge inside the pipeline, where GitLab could otherwise merge before the card exists; it needs "Pipelines must succeed" in the project. Run live in the reference app's order (see "With auto-merge armed" in the README), and run again after the job moved into the policy ([results/hold_under_policy.json](../results/hold_under_policy.json): the job failed, the card posted by itself, one name, one retry, and GitLab merged by itself); it needs one manual retry of the job after the last name, and it showed that the card flow had to read a job that failed on purpose. What defeated it before: the job was defined in the merge request's own CI file, so a merge request could drop it or let it fail. We tried eight ways to merge past it on a throwaway branch ([results/bypass_matrix.json](../results/bypass_matrix.json)): 2 <!-- from: results/bypass_matrix.json:merged --> of the 8 <!-- from: results/bypass_matrix.json:attempts --> merged (a merge request that marks the job allowed to fail, or that stops it from running), and 6 <!-- from: results/bypass_matrix.json:blocked --> were blocked, two of them (deleting the job, emptying its script) only because our own unit tests read the CI file and failed. Then a pipeline execution policy took the job out of the CI file. We wrote eleven new attempts down first ([eval/bypass_matrix_v2_cases.json](../eval/bypass_matrix_v2_cases.json)): delete the project's jobs, add a fake job named `itemator` (allowed to fail, or passing), switch the project pipeline off, skip CI, edit the job file, rewrite the checker, retry without names, forge the summary note, and override the bot variable. On the second run ([results/bypass_matrix_v2.json](../results/bypass_matrix_v2.json); the first crashed and is kept as a log) 0 <!-- from: results/bypass_matrix_v2.json:merged --> of the 11 <!-- from: results/bypass_matrix_v2.json:attempts --> merged. 9 <!-- from: results/bypass_matrix_v2.json:blocked_by_the_itemator_job --> were stopped by the `itemator` job itself failing; the two fake-job attempts never got a pipeline, because the policy refuses a duplicate job name. It counts what we thought of, on one project. What still holds it back: for an agent's merge request no card appears until a person assigns the card account as reviewer, so the job stays held with no thread to answer.
9. **The person who wrote the issue decides** (`names.asker_required` in the policy; six pre-registered replies ran three times live (flow v1.6.0, v1.6.1 and v1.6.3), the same six cases each time, and 18 <!-- from: results/asker_study.json:as_expected --> of 18 <!-- from: results/asker_study.json:cases --> answers in total ended as expected; the record on the issue has not run live yet). When it is on, each thread says `Only the person who wrote the linked issue (@alice) can keep this.`, the reaction flow counts a name, `not an extra` or `always` only from that person, and when every extra has an answer it posts a record on the issue listing what went beyond it and who decided each. A GitLab Insights chart (`.gitlab/insights.yml`, Ultimate) counts merge requests per week by the label the flows left on them.

Only a person's reply counts. Since reaction flow v1.6.3 the flow looks each reply's author up (`/users/<id>`) and leaves out any account GitLab marks as a bot, such as a service account or the Developer Flow's own account. We could not post as a bot to test that branch live (asked to type a name, the Developer Flow declined); the third asker run shows the lookup is made (two lookups in its session) and every person case still ends as expected.

10. **No bot approval.** We tried a step that let the reaction flow post `/approve` and removed it on GitLab staff's advice, because a flow's approval counts as the person who started it and so is not independent; at the Assisted level a person still approves the merge request.
11. **A decision log after the merge** (`itemator/decisions.py`, CI job `decision-log`). The reaction flow ends each merge request with one summary note that lists every extra and who named it. The job reads those notes for the merge requests merged since the previous tag (only notes written by the reaction account are believed, and titles and names are stripped of links and mentions before they reach a release), and on a tag it puts the result in the release description; run by hand on the default branch it gives the same report for the last thirty days. For a merge request with no summary note for the commit it was merged with, it also reads the job's own report on that commit and lists the extras no summary answered as merged without a recorded answer (or says it could not tell: artifacts are kept thirty days); the What shipped page shows the same count. When the reply that decided an extra has lines under its first one, written by the person the summary names in that extra's own thread (opened by the card account), the log quotes them as that person's reason, cut to `REASON` characters (`itemator/decisions.py`) and stripped of links and mentions; it does not guess a reason. It reads merge requests and notes with the job token and writes nothing but the release description. Its first real run was on the merge request that applied the second audit's fixes, which Itemator judged itself: it listed 1 <!-- from: results/decision_log_run.json:stats.merge_requests --> merge request with 2 <!-- from: results/decision_log_run.json:stats.extras --> extras, both kept by their author ([results/decision_log_run.json](../results/decision_log_run.json)). The release path also ran once on a throwaway tag, which wrote the same section into a new release and was deleted afterwards; a release candidate tag (`v0.1.0-rc1`) ran the release path for real on 2026-10-14; the submission tag will be the next release.
12. **Two Agent Skills** (`skills/`) sit in `skills/`; GitLab's Developer Flow read the first one with no setup (one run, below). `stay-inside-the-issue` is for an agent that opens a merge request: keep to the issue, and list anything that needs a person's decision under a `Beyond the issue` heading in the description. `answer-an-itemator-card` helps whoever reads the card: what the lines and the four answers mean. It explains and never answers for the approver.
13. **Which issue a merge request answers.** The job takes the issues GitLab lists as closed by the merge request, else the issues named after a closing word (Closes, Fixes, Resolves, Implements) in the description, else, for a merge request GitLab's Developer Flow opened, the issue its branch is named after (`duo/<kind>/<issue>-...`, read from `CI_MERGE_REQUEST_SOURCE_BRANCH_NAME`, no extra request). We added the last step after reading GitLab's own Developer Flow merge requests for the public replay: many name their issue only under a References heading, with no closing word, while most of their branch names carry its number. A branch name is the author's text, like a description, so it is read only when nothing else names an issue, and only when the description also names that same issue of this project (as `#N`, or as the issue's or work item's URL). We added that second condition after labelling the replay: in some of those merge requests the number in the branch was another merge request or an issue in another project, and the card would have read an unrelated issue. With the condition, such a merge request gets "no issue linked" and a warning instead. When the description says it closes an issue number this project has no issue for, the card's caveat line says so, from GitLab's own "not found" answer; a read that fails says nothing. The Developer Flow opens its merge request under the person who started it, so that person wrote both the issue and the merge request, and the card used to say "No one but the author described this change." Now, when GitLab's own system note on the issue ("mentioned in merge request !N") was written by an account GitLab marks as a bot, the issue is read as that person's ask and the caveat line names the agent account. We found this on the filmed run (!223, !224); a failed read keeps the old sentence.
14. **Scan history** (`itemator/scan.py`, manual CI job `scan-history`). The same rules over the last merge requests already merged into the default branch (fifty unless `SCAN_LAST` says otherwise), so a team can see what went beyond its issue before Itemator was installed. Each merge request is read as it landed: its merge or squash commit against that commit's first parent, with the issues it links read the way the CI job reads them. It writes `scan.md` and `scan.json` as job artifacts, posts nothing and uses no GitLab Credits (no flow runs). A merge request with no merge or squash commit in the clone (a fast-forward merge), or one that cannot be read, is counted as unreadable with the reason.

15. **Run it on your own machine** (`itemator/local.py`). `python -m itemator.local --issue issue.txt` takes a git diff (default: from the merge base with `main` to `HEAD`) and the issue text, runs the same fixed rules as the CI job and prints each extra with the reason the rules gave. It needs no GitLab, no network and no AI model, and it works on a change a person wrote just as well as on one an agent wrote. It does not look new packages up in their registry; the CI job does. With no issue, `--commits` reads the commit messages from the base to `HEAD` as the request, so a person can check an agent's local commits against what the commits say they did before pushing. Add `--map` to also print a table of every changed file with its added and removed lines and one plain label (the kind of extra it is, matches a word in the request, not placed against the request, or no match and no rule lists it), so a reviewer of a large change sees where to look first. The label says which rule listed the file; it does not say the change is right or wrong, and "no match, and no rule lists it" does not mean the file is fine, and "matches a word in the request" does not mean the request asked for that exact change.
16. **The picture of a change** (`itemator/trace.py`, `itemator/mapview.py`, `web/map.html`). `python -m itemator.trace --commits --out trace.json` writes, for each changed file, what the request words, the extras rules, the layout-only check (`itemator/neutral.py`, modified Python files) and the opener (`itemator/unwrap.py`, added or changed binary files) said, and the bin it lands in: listed, opened, neutral or ordinary. Ordinary means nothing listed or proved anything about the file, so read it yourself; it is not a statement that the file is fine. `python -m itemator.mapview` turns trace files into one static page where each file moves through six checks (request, extras rules, layout-only, opener, history, fence) into one of five bins (Play, Pause and Step buttons; with reduced motion set it opens on the end state). The Pages job publishes it under `/map/` with the latest merge to main as a real run and a staged example from `examples/make_example.py`, which is labelled as made up. Standard library and plain SVG; no network, no model.

    `python -m itemator.local --lint-policy` checks the team's `.itemator.toml`: every ignore entry should carry a one-line reason under an optional `[reasons]` table, and a path pattern that matches no file is reported as dead. It exits with a non-zero code when there is something to tidy, so a team can run it in its own CI. The reasons change no extra; they are for the people who read the file later.
17. **"Also checked" on the card** (`itemator/checked.py`, `ci.also_checked`). `itemator/refs.py` reads the commit ids that the commit messages, the title and the description cite (`Fixes:`, `This reverts commit`, `cherry picked from commit`, `commit <id>`) and asks the checkout, then the project's API, whether each exists and whether a quoted title is that commit's title; it reports an id nobody has, or a title that belongs to another commit, and says nothing about an id the API cannot answer for. `itemator/reland.py` looks up each added run of lines (a minimum number of meaningful lines and characters, set in the module) in the file's history with `git log -S` and names the newest commit whose subject starts with "Revert" and whose removed lines contain the run in order (a commit that also re-adds them, or that touched more than twenty files, is skipped). `itemator/revert.py` takes each commit the text says it reverts, reads that commit's diff (the checkout first, the project's API second) and compares it file by file with the change's own diff: the lines it added must be gone and the lines it removed back, and a file with a few lines still in place, a file left untouched, or a change to a file the reverted commit never touched is named (a text that says "partial" is skipped). The same module reads "(cherry picked from commit X)" and stable-kernel "commit X upstream" lines the other way round: the change should add and remove what X added and removed, and the card names what is missing or extra. `itemator/moving.py` reads only the lines a change adds to CI files and Dockerfiles and names an image tagged `latest` or untagged, an include, component or remote include on a branch, and a download piped into a shell. `itemator/shapes.py` reads added lines in any other file but tests, documentation and lock files for three named shapes: text decoded and run, the environment or a credentials file sent to a server, and a download written over a source file within forty consecutive added lines. `itemator/untrusted.py` reads added lines of CI files and shell scripts for GitLab's text-a-person-writes variables (the list is from GitLab's predefined-variables page) on a line with an interpreter that runs text or an AI command-line tool, and for GitHub expressions of pull request, issue and commit text inside `run:` or `script:` lines. `itemator/scanners.py` reads `gl-sast-report.json` and `gl-secret-detection-report.json` from the checkout (GitLab downloads the earlier jobs' artifacts into the Itemator job; the job log shows it), and names findings on lines the change adds and findings elsewhere in files it touches; oversize or odd reports are skipped with a warning. `itemator/record.py` reads the last hundred commits of the target branch and, when at least a set share of the ones that changed shipped files added a record file or edited a changelog, says so on a change that touches shipped files (not tests, documentation, pipeline or hidden files, and not the files the layout check proved) and adds none. When a changed file can change the pipeline (`.gitlab-ci.yml`, `.gitlab/` or `ci/` files), `itemator/pipeline.py` reads GitLab's merged configuration at the merge base and at the head (CI lint, `content_ref`), cuts each into jobs and their keys without a YAML parser, and says which jobs are new, removed or changed (an `allow_failure` or `when` change shows its old and new value); a read GitLab refuses is a warning, never a failure. The CI job runs the same layout-only check and opener on the changed files (up to a fixed cap), and the history check (`itemator/cochange.py`: which modified files never changed in the same commit as any other changed file, read from the target branch's history, only for three to forty modified files) and writes what they found to `checked` in `itemator.json` and, as one sentence, to `card.checked_line`: "Also checked, with no model: some Python files changed only in layout, comments, docstrings or the order of plain functions: ..." and "In the repository's history `x.py` has never changed in the same commit as any other file changed here." and "Opened `tests/files/x.xz`: xz file, unpacks to a program or script". The fence check (`itemator/fence.py`, the old SZZ method run backwards) names lines the change deletes outright that a commit whose subject says it fixes something had added (`git blame -w -M -C` at the base; test, documentation and lock files, blank and comment lines and moved lines are left out; capped per change). It is a fact from the history, not a finding that the deletion is wrong, and we have no outside measure that it catches a real problem: the AIDev sample has too few human comments on removed lines to test it. It is information only: the state, the extras and the exit code never depend on it, a check that breaks on a file leaves that file out with a warning, and a file an extra already lists is not also called layout-only. The card flow posts the line when it is present.

18. **Try a diff in the browser** (`web/try.html`, `web/try_checks.js`, `itemator/tryit.py`). The references-that-move, attack-shape and untrusted-text checks work from added lines alone, so they are written a second time in JavaScript and run on a pasted diff in the visitor's tab. The page carries a Content-Security-Policy that forbids every network request, so a pasted diff cannot be sent anywhere, and it is built only when `results/try_agreement_v2.json` says the two versions agree. `eval/try_agreement.py` compares them on the agent-written commits, a sample of Mesa commits (also with a patch-mail trailer), a corpus of real added lines placed in several file types, and the page's own examples; the rules were written first (`eval/try_agreement_rubric.json`), and after a deliberate-break check showed the first corpus missed deleted files and some paths, a second run was added and both are published. Agreement says the two versions behave alike, not that the checks are right; their rates and incident replays are in the results files the page's table reads.

## Live runs

The notes of one real run, in order and unedited, are in [results/a_real_run.md](../results/a_real_run.md).

**Real agent runs.** We assigned two small issues to GitLab's own Developer Flow. For the first (look up registry facts in parallel) the agent changed only the code and its tests, and the card said so. For the second ("make the itemator job faster") it changed only `.gitlab-ci.yml`, a file the issue never mentions: Itemator flagged it, the approver typed the name, and the flow settled it. An agent that changes how a job runs is doing what it was asked, and a person still decides to keep it. We then added the first skill and gave the Developer Flow the same issue again: this time its description ended with a `Beyond the issue` section naming `.gitlab-ci.yml` and why. That is one run on one issue, so it shows that the skill is read, not how often it helps. The rules still flag the file either way; the skill only makes the agent say it.

**Eight runs written down first.** Later we wrote eight issues before running any of them ([eval/field_study_issues.json](../eval/field_study_issues.json): four plain, two that tempt an agent to add a package, two that name a CI change) and gave each to the Developer Flow, one at a time, with `AGENTS.md` and the skill in place. It opened a merge request every time, with a median of 17.5 <!-- from: results/field_study.json:tool_calls_median --> tool calls. The `itemator` job found no extra in any of the eight (in two it could not place one file, which the card does not show when the issue's author opened the run), and every description had a `Beyond the issue` section: five said "Nothing", three listed edits the agent made. So with those two files in the repository the rules found nothing beyond the issue, and the card asked no question. The section test was made stricter after the first two runs and applied again to their saved descriptions, and the tool-call counts were read again after every session had ended. That does not show the problem is rare: it is eight runs of one agent on issues we wrote, all started by the person who wrote them, and we ran no control without `AGENTS.md`. The counts are in [results/field_study.json](../results/field_study.json); nothing was merged.

Every step ran live on GitLab.com in this project, on throwaway merge requests and issues in this project, closed afterwards. The merge requests that tested naming, `split` and `remove` were prepared by us with planted extras (a made-up package name, a comment line in the CI file, a backup file). The Developer Flow runs above were not prepared: the agent's own work on issues we wrote.
