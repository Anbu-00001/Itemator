# How Itemator works, in full

The front page ([README](../README.md)) has the pitch, the diagram and the first three steps. This page has the rest of the steps and the live runs behind them.

## What each flow can write
The tool lists are in the flow files (`toolset:`). A tool a flow does not hold, it cannot call; what a held tool is told to do is in the flow's prompt, which our tests read (and which a hostile text could in principle argue with: see the injection study in [docs/measurements.md](measurements.md)).

| Flow | Tools that change something | What we use them for | Tools it does not hold |
|---|---|---|---|
| Card (`flows/itemator_card.yml`) | `create_merge_request_note`, `create_merge_request_diff_note`, `update_merge_request` | the card, one thread per extra on the changed line, Draft and labels | any commit or branch tool, any approval, any merge |
| Reaction (`flows/itemator_react.yml`) | `reply_to_discussion`, `set_discussion_resolved`, `create_merge_request_note`, `update_merge_request`, `create_issue_note`, `create_commit`, `create_merge_request` | answers in threads, the summary, labels and Draft, the record on the issue; `create_commit` and `create_merge_request` only for `split`, `remove` and `always`, each asked for by a typed answer | any approval, any merge |

The commit and merge-request tools are the widest ones. The reaction flow's prompt limits them to the merge request's own branch (`split`, `remove`) and to one new branch for the one-line policy change (`always`); a prompt is not a permission, and a stricter setup would split the reaction flow in two so the commit tools sit in a flow that only a `split`, `remove` or `always` reply can start. We have not built that split.

## The other steps

4. **For a new dependency the thread also carries facts from PyPI, npm or crates.io, and OSV**: whether the package exists, when it was first released, how many releases it has, its licence as the publisher declares it, and the number of known advisories. Only facts; no score. The lookup validates every name, reaches four hosts, and never fails the job.
5. **A team can set its own rules in `.itemator.toml`**, read from the branch the merge request targets, so the merge request cannot change the rules it is judged by. The file can require that someone other than the author names each extra, or quiet whole kinds of extras and paths; it can never quiet a binary file, a change to the policy itself, or a dependency the registry did not find. The `itemator` job also runs the checker exported from the target branch, and ignores git attributes in the checkout, so a merge request cannot hide its diff.

6. **Each thread says whether the author's own description mentions the extra**, in one of three fixed sentences: it lists the extra under a `Beyond the issue` heading, it names it, or it does not mention it. None of the author's words is ever copied into the thread, and the extras the description does not mention come first. It is a fact, not an approval: an author who names every extra still gets every thread. Across the 75 <!-- from: results/silent_extras.json:summary.per_sample.total.extras --> extras the rules found in our five samples, the pull request's own text named 12 <!-- from: results/silent_extras.json:summary.per_sample.total.named --> (a plain word match; a paraphrase does not count).
7. **An answer can become a team rule, through review.** For an extra that is a single CI or config file or a stray file, the thread also offers `always`. The flow keeps the extra and opens a merge request into the target branch whose whole change is one line of `.itemator.toml` (the file is added to `ignore.paths`); merging it stops the questions about that file on later merge requests. Binaries, agent instruction files, package manifests and changes to the policy are never offered. We ran this end to end on a throwaway branch, and again after the reaction flow's prompt was tightened (the one-line check now reads the diff GitLab reports): the answer opened the one-line merge request, and after it was merged the same edit in a new merge request was listed as quieted by the team policy. It is a choice for a team to make, and it trades fewer questions for more silence. A policy merge request that no issue describes also gets a thread, for the policy file itself, and stays in Draft until a person links the issue it answers (we checked this on a throwaway branch).
8. **An optional hold** (`names.hold_until_named = true` in the policy). The `itemator` job then fails while a kept extra has no name, and passes again when the reaction account's summary for the current head commit exists (retry the job after the last name). It is meant for loops that arm auto-merge inside the pipeline, where GitLab could otherwise merge before the card exists; it needs "Pipelines must succeed" in the project. Run live in the reference app's order (see the top of the README), and run again after the job moved into the policy ([results/hold_under_policy.json](../results/hold_under_policy.json): the job failed, the card posted by itself, one name, one retry, and GitLab merged by itself); it needs one manual retry of the job after the last name, and it showed that the card flow had to read a job that failed on purpose. What defeated it before: the job was defined in the merge request's own CI file, so a merge request could drop it or let it fail. We tried eight ways to merge past it on a throwaway branch ([results/bypass_matrix.json](../results/bypass_matrix.json)): 2 <!-- from: results/bypass_matrix.json:merged --> of the 8 <!-- from: results/bypass_matrix.json:attempts --> merged (a merge request that marks the job allowed to fail, or that stops it from running), and 6 <!-- from: results/bypass_matrix.json:blocked --> were blocked, two of them (deleting the job, emptying its script) only because our own unit tests read the CI file and failed. Then a pipeline execution policy took the job out of the CI file. We wrote eleven new attempts down first ([eval/bypass_matrix_v2_cases.json](../eval/bypass_matrix_v2_cases.json)): delete the project's jobs, add a fake job named `itemator` (allowed to fail, or passing), switch the project pipeline off, skip CI, edit the job file, rewrite the checker, retry without names, forge the summary note, and override the bot variable. On the second run ([results/bypass_matrix_v2.json](../results/bypass_matrix_v2.json); the first crashed and is kept as a log) 0 <!-- from: results/bypass_matrix_v2.json:merged --> of the 11 <!-- from: results/bypass_matrix_v2.json:attempts --> merged. 9 <!-- from: results/bypass_matrix_v2.json:blocked_by_the_itemator_job --> were stopped by the `itemator` job itself failing; the two fake-job attempts never got a pipeline, because the policy refuses a duplicate job name. It counts what we thought of, on one project. What still holds it back: for an agent's merge request no card appears until a person assigns the card account as reviewer, so the job stays held with no thread to answer.
9. **The person who wrote the issue decides** (`names.asker_required` in the policy; six pre-registered replies ran twice live (flow v1.6.0 and v1.6.1), the same six cases each time, and 12 <!-- from: results/asker_study.json:as_expected --> of 12 <!-- from: results/asker_study.json:cases --> answers in total ended as expected; the record on the issue has not run live yet). When it is on, each thread says `Only the person who wrote the linked issue (@alice) can keep this.`, the reaction flow counts a name, `not an extra` or `always` only from that person, and when every extra has an answer it posts a record on the issue listing what went beyond it and who decided each. A GitLab Insights chart (`.gitlab/insights.yml`, Ultimate) counts merge requests per week by the label the flows left on them.
10. **No bot approval.** We tried a step that let the reaction flow post `/approve` and removed it on GitLab staff's advice, because a flow's approval counts as the person who started it and so is not independent; on the Supervised path a person still approves the merge request.
11. **A decision log after the merge** (`itemator/decisions.py`, CI job `decision-log`). The reaction flow ends each merge request with one summary note that lists every extra and who named it. The job reads those notes for the merge requests merged since the previous tag (only notes written by the reaction account are believed, and titles and names are stripped of links and mentions before they reach a release), and on a tag it puts the result in the release description; run by hand on the default branch it gives the same report for the last thirty days. It reads merge requests and notes with the job token and writes nothing but the release description. Its first real run was on the merge request that applied the second audit's fixes, which Itemator judged itself: it listed 1 <!-- from: results/decision_log_run.json:stats.merge_requests --> merge request with 2 <!-- from: results/decision_log_run.json:stats.extras --> extras, both kept by their author ([results/decision_log_run.json](../results/decision_log_run.json)). The release path also ran once on a throwaway tag, which wrote the same section into a new release and was deleted afterwards; a release candidate tag (`v0.1.0-rc1`) ran the release path for real on 2026-10-14; the submission tag will be the next release.
12. **Two Agent Skills** (`skills/`) sit in `skills/`; GitLab's Developer Flow read the first one with no setup (one run, below). `stay-inside-the-issue` is for an agent that opens a merge request: keep to the issue, and list anything that needs a person's decision under a `Beyond the issue` heading in the description. `answer-an-itemator-card` helps whoever reads the card: what the lines and the four answers mean. It explains and never answers for the approver.

## Live runs

**Real agent runs.** We assigned two small issues to GitLab's own Developer Flow. For the first (look up registry facts in parallel) the agent changed only the code and its tests, and the card said so. For the second ("make the itemator job faster") it changed only `.gitlab-ci.yml`, a file the issue never mentions: Itemator flagged it, the approver typed the name, and the flow settled it. An agent that changes how a job runs is doing what it was asked, and a person still decides to keep it. We then added the first skill and gave the Developer Flow the same issue again: this time its description ended with a `Beyond the issue` section naming `.gitlab-ci.yml` and why. That is one run on one issue, so it shows that the skill is read, not how often it helps. The rules still flag the file either way; the skill only makes the agent say it.

**Eight runs written down first.** Later we wrote eight issues before running any of them ([eval/field_study_issues.json](../eval/field_study_issues.json): four plain, two that tempt an agent to add a package, two that name a CI change) and gave each to the Developer Flow, one at a time, with `AGENTS.md` and the skill in place. It opened a merge request every time, with a median of 17.5 <!-- from: results/field_study.json:tool_calls_median --> tool calls. The `itemator` job found no extra in any of the eight (in two it could not place one file, which the card does not show when the issue's author opened the run), and every description had a `Beyond the issue` section: five said "Nothing", three listed edits the agent made. So with those two files in the repository the rules found nothing beyond the issue, and the card asked no question. The section test was made stricter after the first two runs and applied again to their saved descriptions, and the tool-call counts were read again after every session had ended. That does not show the problem is rare: it is eight runs of one agent on issues we wrote, all started by the person who wrote them, and we ran no control without `AGENTS.md`. The counts are in [results/field_study.json](../results/field_study.json); nothing was merged.

Every step ran live on GitLab.com in this project, on throwaway merge requests and issues in this project, closed afterwards. The merge requests that tested naming, `split` and `remove` were prepared by us with planted extras (a made-up package name, a comment line in the CI file, a backup file). The Developer Flow runs above were not prepared: the agent's own work on issues we wrote.
